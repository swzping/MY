# Agent Stack 实战手册

这篇用来做决策：遇到一个 AI / Agent 需求时，应该写普通脚本、写 Skill、接 MCP，还是上 LangGraph。

## 快速决策表

| 需求特征 | 优先选择 | 原因 |
| --- | --- | --- |
| 一次性任务，结果可人工检查 | 普通脚本 / 手工流程 | 成本最低，最快验证 |
| 重复任务，但步骤固定 | Skill | 把方法、模板、检查清单沉淀下来 |
| 需要访问外部系统或私有数据 | MCP | 给 AI 客户端一个稳定、可控的接口 |
| 多步骤、有分支、有循环、有状态 | LangGraph | 图结构更适合显式编排复杂流程 |
| 多客户端都要用同一套能力 | MCP | 协议层复用，比写死在某个客户端里稳 |
| 多角色协作、需要复核和回退 | LangGraph + Skill | 用图管流程，用 Skill 管方法 |
| 既有复杂流程，又要接外部系统 | LangGraph + MCP | 图负责编排，MCP 负责能力接入 |
| 涉及真实账户、交易、生产系统 | MCP + 权限 + 审计 + 人工确认 | 先保证边界和可追责，再谈智能化 |

## 判断顺序

### 1. 这个需求能不能用普通脚本解决？

优先问：

- 输入是否清楚？
- 输出是否稳定？
- 是否只需要调用一个或少数几个 API？
- 是否不需要长期记忆、状态恢复、多角色讨论？

如果答案大多是“是”，先写脚本。脚本可以被人运行，也可以被 Skill 或 Agent 调用，是很好的底座。

### 2. 这个需求是不是会重复发生？

如果会重复，考虑写 Skill。

适合写 Skill 的信号：

- 任务有固定流程。
- 经常需要同一套检查清单。
- 有标准输出格式。
- 有参考资料、模板、命令或脚本需要绑定在一起。
- 希望不同项目里也能复用这套方法。

例子：

- 每天整理 AI 新闻趋势。
- 做代码 review。
- 分析一只股票的技术面和资金面。
- 生成 Word、PPT、Excel 类文件并做视觉检查。

### 3. 这个需求是否需要连接外部系统？

如果需要连接数据库、SaaS、内部 API、浏览器、设计工具、文件系统或知识库，考虑 MCP。

适合写 MCP server 的信号：

- AI 客户端需要读取或操作外部系统。
- 能力不只给一个 agent 用。
- 需要统一认证、权限、日志和错误处理。
- 工具返回结构化数据，比网页搜索或复制粘贴可靠。
- 希望把“能做什么”明确暴露给客户端，而不是把密钥和业务逻辑散在 prompt 里。

例子：

- 查询公司内部知识库。
- 操作 Figma、Notion、GitHub、数据库。
- 给股票研究 Agent 提供行情、研报、公告数据。
- 给交易系统提供 paper trading 查询和受限操作。

### 4. 这个需求是否需要复杂流程编排？

如果有状态、分支、循环、多 Agent、人工审批或失败恢复，考虑 LangGraph。

适合上 LangGraph 的信号：

- 流程不是线性的。
- 某一步结果决定下一步走向。
- 需要反复调用工具直到满足条件。
- 需要保存中间状态，甚至中断后恢复。
- 需要多个角色协作，例如 planner、researcher、executor、reviewer。
- 需要可观察地追踪每一步为什么发生。

例子：

- 自动研究一个行业并生成报告：检索、筛选、提纲、写作、复核、引用检查。
- 金融研究 Agent：行情/新闻/基本面/技术分析、多空辩论、交易建议、风险复核。案例见 [TradingAgents](tradingagents-notes.md)。
- 多 Agent 编程流程：需求澄清、计划、实现、测试、review、修复。
- 客服 Agent：识别意图、查订单、判断权限、请求人工确认、执行操作。

## 常见架构模式

### 模式一：Skill + 脚本

适合个人知识库和轻量自动化。

```text
skill/
  SKILL.md
  templates/
  scripts/
```

优点：

- 简单、便宜、可维护。
- 对单人工作流很友好。
- 失败时容易人工接管。

风险：

- 不适合复杂状态机。
- 脚本权限需要自己管。

### 模式二：Skill + MCP

适合“有固定方法，还要连外部系统”的任务。

```text
AI client
  -> Skill: 告诉 agent 怎么做
  -> MCP server: 提供数据和动作
```

例子：

- Skill 规定“先查公告，再看研报，再看资金面，最后输出风险提示”。
- MCP server 提供“查公告、查研报、查资金流”的工具。

优点：

- 方法和能力分离。
- MCP 能被多个客户端复用。

风险：

- MCP 工具边界要设计清楚。
- Skill 不能替代权限控制。

### 模式三：LangGraph + MCP

适合企业级或垂直行业 Agent。

```text
LangGraph
  nodes:
    plan
    retrieve_via_mcp
    analyze
    ask_human
    execute_via_mcp
    verify
```

优点：

- 流程、状态、工具调用都清楚。
- 适合审计、调试和持续优化。

风险：

- 架构成本更高。
- 需要认真设计状态、错误处理和观测。

金融研究里的对应关系：

- [TradingAgents](tradingagents-notes.md) 更偏 `LangGraph + 项目内工具/vendor`，先把多角色研究流程跑通。
- 如果要接入自己的 A 股数据、研报库、交易账户或风控系统，应把这些外部能力做成 MCP 或受控 API，并默认只读、paper-only、可审计。

### 模式四：Skill + LangGraph + MCP

适合长期沉淀的复杂业务。

- Skill：定义一类任务的工作方法和验收规则。
- LangGraph：实现可执行流程。
- MCP：连接外部系统。
- Eval：验证结果是否可靠。

这种模式不是起点，通常是从脚本、Skill、MCP 逐步长出来的。

## 权限与安全检查

只要 Agent 能操作外部系统，就要问：

- 工具是否默认只读？
- 写操作是否需要人工确认？
- 是否区分 sandbox、paper、production？
- 是否记录谁在什么时候调用了什么工具？
- 是否能回放输入、输出和错误？
- 是否能限制数据范围、账号范围和操作范围？
- 密钥是否只在服务端保存，而不是暴露给模型或文档？

尤其是交易、支付、账号管理、生产数据库、客户数据、公司内部资料，不能只靠 prompt 约束。

## 最小可行路线

对一个新想法，可以这样推进：

1. 先写普通脚本，确认数据和输出有价值。
2. 把稳定流程沉淀成 Skill。
3. 如果需要复用外部能力，把脚本升级成 MCP server。
4. 如果流程变复杂，再用 LangGraph 编排。
5. 最后补 eval、日志、权限和文档。

这条路线的好处是每一步都有可用产物，不会为了架构而架构。
